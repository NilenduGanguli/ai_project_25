## Indian Passport Schema

### Document Type: `passport`
### Country Code: `IN`
### Sample Document

**Test File:** `test/Passport.pdf`

**Document Image Preview:**
- Indian Passport booklet page
- Contains personal information, photo, and Machine Readable Zone (MRZ)
- Government of India seal and security features
- Multiple language text (English and Hindi)

### Schema Definition

This schema captures all relevant information from an Indian passport document.

#### Personal Information Fields

| Field Name | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `passport_number` | string | Yes | Unique alphanumeric passport number | `S0018565` |
| `surname` | string | Yes | Surname/Last name in capital letters | `GANGULI` |
| `given_names` | string | Yes | Given names (First + Middle names) | `NILENDU` |
| `nationality` | string | Yes | Nationality of passport holder | `INDIAN` |
| `sex` | string | Yes | Gender: M (Male), F (Female), O (Other) | `M` |
| `date_of_birth` | date | Yes | Date of birth in DD/MM/YYYY format | `11/11/1999` |
| `place_of_birth` | string | No | Place of birth as shown on passport | `BIDHANNAGAR, WEST BENGAL` |

#### Passport Details

| Field Name | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `date_of_issue` | date | Yes | Date of issue in DD/MM/YYYY format | `16/03/2018` |
| `date_of_expiry` | date | Yes | Date of expiry in DD/MM/YYYY format | `15/03/2028` |
| `place_of_issue` | string | No | Place where passport was issued | `KOLKATA` |
| `type` | string | No | Type of passport (P for Regular) | `P` |
| `country_code` | string | No | ISO country code | `IND` |
| `old_passport_number` | string | No | Previous passport number if any | `M1234567` |

#### Machine Readable Zone (MRZ)

| Field Name | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `mrz_line_1` | string | Yes | First line of MRZ (44 characters) | `P<INDGANGULI<<NILENDU<<<<<<<<<<<<<<<<<<<<` |
| `mrz_line_2` | string | Yes | Second line of MRZ (44 characters) | `S0018565<8IND9911116M2803159<<<<<<<<<<<<06` |

#### Family Information

| Field Name | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `name_of_father_legal_guardian` | string | No | Father's name or legal guardian | `LATE SHRI XXXXX GANGULI` |
| `name_of_mother` | string | No | Mother's name | `SMT. YYYY GANGULI` |
| `name_of_spouse` | string | No | Spouse name (if applicable) | `N/A` |

#### Address Information

| Field Name | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `address_line_1` | string | No | First line of address | `123 EXAMPLE STREET` |
| `address_line_2` | string | No | Second line of address | `NEAR ABC PARK` |
| `city` | string | No | City name | `KOLKATA` |
| `state` | string | No | State name | `WEST BENGAL` |
| `pin_code` | string | No | Postal code | `700000` |
| `file_number` | string | No | File number on passport | `KOL1234567` |

#### Visual Verification Fields

| Field Name | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `photo_present` | boolean | Yes | Whether passport photo is visible and clear | `true` |
| `signature_present` | boolean | Yes | Whether signature is visible | `true` |
| `hologram_present` | boolean | No | Whether security hologram is visible | `true` |
| `barcode_qr_present` | boolean | No | Whether barcode/QR code is present | `true` |

#### Validation Fields

| Field Name | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `is_document_correct` | boolean | Yes | Whether document appears to be a valid passport | `true` |
| `is_data_readable` | boolean | Yes | Whether text is clear and readable | `true` |
| `is_document_damaged` | boolean | No | Whether document shows signs of damage | `false` |
| `confidence_score` | number | No | Overall confidence in extraction (0-1) | `0.95` |

## Schema Structure

### Field Definition Format

Each field in a schema follows this structure:

```json
{
  "field_name": {
    "type": "string|integer|boolean|date|number",
    "description": "Human-readable description of the field",
    "required": true|false,
    "example": "Sample value",
    "pattern": "regex pattern (optional)",
    "min_length": 0,
    "max_length": 100
  }
}
```

### Field Properties

| Property | Type | Required | Description |
|----------|------|----------|-------------|
| `type` | string | Yes | Data type: string, integer, boolean, date, number |
| `description` | string | Yes | Clear description of what the field contains |
| `required` | boolean | Yes | Whether field must be present in extraction |
| `example` | any | No | Example value for the field |
| `pattern` | string | No | Regex pattern for validation |
| `min_length` | integer | No | Minimum length for string fields |
| `max_length` | integer | No | Maximum length for string fields |

## Field Types

### Supported Data Types

1. **string**
   - Text data of any length
   - Most common type for names, addresses, IDs
   - Example: `"NILENDU GANGULI"`

2. **integer**
   - Whole numbers only
   - Used for counts, years
   - Example: `2018`

3. **number**
   - Decimal numbers
   - Used for amounts, scores
   - Example: `0.95`, `1234.56`

4. **date**
   - Date values in DD/MM/YYYY format
   - Used for birth dates, issue dates, expiry dates
   - Example: `"11/11/1999"`

5. **boolean**
   - True/false values
   - Used for presence checks, validation flags
   - Example: `true`, `false`

## Validation Rules

### Required Fields

- All schemas must include validation fields:
  - `is_document_correct`: Overall document validity
  - `photo_present`: Photo visibility (for ID documents)
  - `signature_present`: Signature visibility

### Document-Specific Rules

#### Passport
- MRZ lines must be exactly 44 characters
- Passport number follows pattern: Letter + 7 digits
- Dates must be in DD/MM/YYYY format

#### PAN Card
- PAN number must be exactly 10 characters
- Pattern: 5 letters + 4 digits + 1 letter
- All text in capital letters

## Schema Versioning

### Version Management

Schemas are versioned using integer version numbers starting from 1.

#### Version States

1. **IN_REVIEW** (Status)
   - Newly generated schema
   - Requires human approval
   - Cannot be used for extraction

2. **ACTIVE** (Status)
   - Approved and ready for use
   - Used for data extraction
   - Only one active version per document type/country

3. **DEPRECATED** (Status)
   - Previously active, now superseded
   - Kept for historical reference
   - Cannot be used for new extractions

### Version Flow

```
[New Document] → Generate Schema (v1, IN_REVIEW)
                        ↓
                   Approve Schema
                        ↓
                (v1, ACTIVE) ← Used for extraction
                        ↓
                Modify Schema → New version (v2, IN_REVIEW)
                        ↓
                   Approve v2
                        ↓
                (v1, DEPRECATED) + (v2, ACTIVE)
```

### Modification Process

1. **Request Modification** on latest version
   - Specify field changes (add/update/remove)
   - Provide change description

2. **System Actions**
   - Validates modifications
   - Creates new version
   - Deprecates old version
   - New version goes to IN_REVIEW

3. **Approval**
   - Human reviews new schema
   - Approves changes
   - New version becomes ACTIVE

### Schema Generation Process

**Step 1: Document Upload**
```bash
POST /extract
Content-Type: multipart/form-data

file: passport.pdf
```

**Step 2: Classification**
- Document Type: `passport`
- Country: `IN`
- Confidence: 0.95

**Step 3: Schema Generation** (if no active schema exists)
- LLM analyzes document structure
- Identifies 30+ fields
- Generates schema with field types and descriptions
- Saves as IN_REVIEW status

**Step 4: Schema Approval**
```bash
PUT /schemas/{schema_id}/approve
```

**Step 5: Data Extraction**
- Uses approved schema
- Extracts structured data
- Returns JSON output

## Best Practices

### Schema Design

1. **Be Specific**
   - Use clear, descriptive field names
   - Provide detailed descriptions
   - Include example values

2. **Mark Required Fields**
   - Only mark truly essential fields as required
   - Most fields should be optional
   - Always include validation fields as required

3. **Use Appropriate Types**
   - Dates → `date` type
   - Flags → `boolean` type
   - IDs/Text → `string` type
   - Counts → `integer` type

4. **Include Validation**
   - Add `is_document_correct` field
   - Add presence checks for visual elements
   - Use patterns for structured IDs

### Schema Modification

1. **Document Changes**
   - Always provide change_description
   - Explain why modification is needed
   - List affected fields

2. **Test Before Approval**
   - Review generated schema carefully
   - Check field types and descriptions
   - Verify required/optional settings

3. **Version Control**
   - Keep deprecated schemas for reference
   - Track version history
   - Document breaking changes

## Troubleshooting

### Low Confidence Scores

If extraction confidence is below 0.8:
- Image quality may be poor
- Document may be partially visible
- Wrong document type may be detected

### Missing Fields

If expected fields are not extracted:
- Field may not be visible in document
- Field name in schema may not match document
- LLM may have misread the field

### Incorrect Data Types

If data types don't match expected:
- Review schema field definitions
- Update schema with correct types
- Re-approve modified schema

## Document Image Specifications

### Supported Formats
- **PDF**: application/pdf
- **JPEG**: image/jpeg, image/jpg
- **PNG**: image/png

### Recommended Quality
- Resolution: Minimum 300 DPI
- File Size: 100KB - 5MB
- Color: RGB or Grayscale
- Orientation: Portrait (for most documents)

### Image Requirements
- Clear, legible text
- No heavy shadows or glare
- All fields visible
- Document not cropped
- High contrast between text and background
